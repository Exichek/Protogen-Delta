# Поиск эпизодической памяти

Раньше `MemoryService.context` сравнивал слова запроса только с 20 последними
эпизодами. Теперь `MemoriesRepository.search` использует SQLite FTS5 и ищет среди
всех сохранённых эпизодов нужного пользователя. Никаких новых зависимостей или
запросов к модели для поиска не требуется.

## Что попадает в ответ

Оригинал эпизода сохраняется отдельно от поискового представления. Поиск
нормализует регистр, Unicode и `ё/е`, исключает служебные слова и снимает русские
окончания по [алгоритму Snowball](https://snowballstem.org/algorithms/russian/stemmer.html).
Например, «дракон», «драконов» и «драконами» дают одну поисковую основу.
Это не семантическая память: синонимы, неправильные формы, опечатки и изменения
основы вроде «человек/люди» могут не совпадать. Английские слова сравниваются
после нормализации регистра, без снятия окончаний.

Результаты ранжируются по BM25. Важность даёт небольшой множитель к релевантности
(15% за уровень сверх первого); при одинаковой оценке выбираются новые записи.
По умолчанию в контекст включаются до трёх результатов и не более 2000 символов.
Если совпадений нет, сохраняется прежняя возможность использовать последние
эпизоды для продолжения разговора. Пустой или слишком маленький бюджет контекста
не вызывает дополнительных запросов к модели.

Запрос ограничен 16 уникальными словами. Пользовательские операторы, кавычки и
скобки не исполняются как синтаксис FTS: выражение собирается из нормализованных
слов и передаётся параметром. Запрос всегда фильтруется по владельцу. Личные
эпизоды по-прежнему не передаются в групповой ответ.

## Важность и срок хранения

Имеющиеся записи получают важность 1. Прямая просьба в начале сообщения
«Запомни…», «Пожалуйста, запомни…» или «Remember…» получает важность 3. Цитата
такой просьбы внутри обычного сообщения не повышает важность. Это простой
детерминированный признак, а не оценка значимости моделью. Само сохранение эпизода
не означает, что извлечение постоянного факта прошло успешно.

При повторе эпизода обновляется дата, важность не понижается. Для каждого из
трёх типов остаётся лимит 50 записей; сначала сохраняются более важные, затем
более новые. Уже удалённые прежним лимитом записи восстановить невозможно.
Автоматические сводки и эмбеддинги на этом этапе не добавлены.

## Миграция, исправление и забывание

При первом запуске к `memories.db` добавляются `search_text`, `importance`,
виртуальная таблица FTS5 и триггеры синхронизации. Поисковое представление старых
эпизодов строится в той же транзакции. Исходные тексты, даты, ID, активности и
настройки проактивных сообщений сохраняются.

Версия нормализации хранится отдельно. При её изменении индекс перестраивается.
Записи, добавленные старой версией бота после временного отката, индексируются
при следующем запуске новой версии. Отсутствующий индекс также восстанавливается
из оригинальных эпизодов.

Исправление или забывание факта удаляет связанные эпизоды как по исходному
тексту, так и по совпадению нормализованных слов. Например, удаление «Илья»
удаляет запись «говорили с Ильёй». Это может удалить целый эпизод вместе с
другими обсуждавшимися темами. Полный сброс удаляет эпизоды только этого
пользователя; триггеры очищают индекс в той же транзакции.

## Автоматические проверки

`tests/test_memory_search.py` проверяет старую запись за пределами последних
20 эпизодов, русские словоформы, ранжирование, важность, переполнение, обновление
дубликата, миграцию старой базы, восстановление индекса, забывание, сброс и
изоляцию пользователей. Интеграционный сценарий проверяет реальный контекст
`ResponseEngine` с временной SQLite-базой и моделью-заглушкой. Эти проверки уже
входят в обычный CI и не используют платные API или сообщения Telegram.

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_memory_search.py tests/test_user_facts.py -q --no-cov -p no:cacheprovider
```

Ручной `scripts/evaluate_dialogue.py` теперь подключает объединённый
`InteractionClassifier`, как работающий бот. В отчёте у каждого сценария есть
`passed` и `errors`; нарушение ожиданий завершает процесс с кодом 1. Добавлены
проверки точного названия старого проекта, отсутствия чужой памяти и отсутствия
удалённого названия после забывания. Для них используется временная база.
Это ограниченные проверки известных ожиданий, а не универсальная оценка
качества речи или полноценный аудит защиты.

Ручной прогон вызывает настоящую модель и расходует API-бюджет. Во время
разработки изменения он не запускался. Его отчёт содержит тестовые сообщения и
ответы модели; файл следует хранить локально и проверять перед публикацией.
