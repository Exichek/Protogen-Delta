# Онлайн-копия данных и проверка восстановления

Новая утилита `python -m protogen_delta.backup_snapshot` копирует работающий
бот без его остановки. Каждая SQLite читается через `Connection.backup`,
включая зафиксированные записи WAL; копия нормализуется в самостоятельную
базу без WAL/SHM. У баз могут быть разные моменты снимка: общей транзакции
между ними и JSON нет. Это явно онлайн-копия, не обещание общего момента времени.

Копируются корневые `.db` и `.json` каталога данных, включая журнал доставки,
расходы, возрастные признаки и полный архив, если он включён. `.env`, ключи,
каталоги, логи и файлы вне каталога данных не копируются; ссылки отклоняются.
Каждая база проходит `integrity_check`, JSON разбирается. Манифест содержит
только имена файлов, размеры, SHA-256, версию формата и дату. Сам снимок
содержит личные данные, его нельзя публиковать или помещать в git.

```bash
python -m protogen_delta.backup_snapshot create --source /app/data --destination /app/data/backups/daily-example
python -m protogen_delta.backup_snapshot verify --source /app/data/backups/daily-example
python -m protogen_delta.backup_snapshot pack --source /app/data/backups/daily-example --destination /app/data/backups/daily-example.zip
```

Восстановление всегда создаёт новый каталог и не подменяет рабочие данные:

```bash
python -m protogen_delta.backup_snapshot restore-zip --source /app/data/backups/daily-example.zip --destination /app/data-restored-example
```

Для переключения работающего бота на восстановленные данные нужна отдельная
операция с остановкой процесса. Сам тест восстановления бот не запускает.
ZIP ограничен 1025 записями и 2 ГБ распакованных данных; имена плоские,
переходы каталогов и повторы не допускаются. Создание ZIP свыше этого предела
тоже отклоняется. Размеры и контрольные суммы проверяются до восстановления;
проверяется отсутствие незаявленных файлов. Ошибка оставляет копию неуспешной.

Для выбранного пользователем переноса через компьютер есть
`scripts/backup_delta.py`. Он требует SSH-хост, абсолютный путь репозитория
на сервере и отдельный локальный каталог. Доступ — существующая SSH-настройка,
секреты не передаются через аргументы. Утилита создаёт новый снимок установленным
пакетом внутри Docker, получает ZIP через SCP, сверяет SHA-256 и выполняет
пробное восстановление в временный каталог. Вывод содержит только путь,
контрольную сумму и количества, без содержимого таблиц.

Квитанция явно содержит `restoration_verified=true` и
`cloud_upload_verified=false`: скачивание на компьютер не является загрузкой
в Google Drive. Успех облачного шага должен подтверждаться отдельно метаданными
загруженного файла. Нужны подключённый Google Drive, включённый компьютер
и работающее приложение Codex. Автоматизация должна сообщать о недоступном
подключении, а не считать локальную копию облачной. Общий доступ к файлам
не включается. Существующие копии автоматически не удаляются.

Старый `maintenance backup/restore` остаётся офлайн-операцией с `--bot-stopped`.
Он дополнен журналом `delivery_ledger.db`, который прежде не входил в список.
Без этого после восстановления терялась бы защита от повторной обработки.

Тесты проверяют WAL с активным писателем и незавершённой транзакцией,
сохранение возрастного признака и журнала доставки, ZIP-круг, повреждения,
незаявленные файлы, небезопасные пути, лимит распаковки, запрет перезаписи,
несовпадение SHA после SCP и отсутствие ложной квитанции облачного успеха.
